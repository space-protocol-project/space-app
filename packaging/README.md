# Установщики Space

Workflow `desktop.yml` собирает приложение и сохраняет установщики и SHA-256 в артефактах GitHub Actions на 30 дней. Он запускается вручную и при изменениях клиента в main/PR. Это пока сборки приложения, домашний сервер в них не включён.

- Windows x64: Inno Setup, установка без прав администратора в профиль пользователя, ярлык и удаление через настройки Windows. Компилятор берётся из образа GitHub runner.
- macOS: DMG с Space.app и ссылкой Applications; архитектура указана в имени файла. Подпись Apple и notarization ещё не настроены, Gatekeeper может препятствовать запуску.
- Linux x64: самораспаковывающийся `.run`, установка в `~/.local/opt/space`, команда `~/.local/bin/space`, ярлык приложения. `--extract DIR` распаковывает без установки. Нужны совместимая glibc (сборка Ubuntu 22.04), GTK 3 и libsecret; это не универсальный пакет для всех дистрибутивов.
- Android: подписанный APK для arm64-v8a, armeabi-v7a и x86_64, Android 7.0 и новее. При обновлении сохраняются package ID и сертификат, versionCode увеличивается. JVM-тесты выполняются без устройства и эмулятора; физическая приёмка остаётся отдельной проверкой.

Сборка Linux устанавливает clang, cmake, ninja-build, pkg-config, libgtk-3-dev и libsecret-1-dev только на одноразовом runner. Локальная установка зависимостей и Docker не требуются для изменения проекта.

Поддержка сборки macOS/Linux не заменяет проверки на физических системах: защищённое хранилище, камера и восстановление требуют отдельных проверок. Камера сейчас реализована для Windows.

## Публикация в GitHub Releases

Тег `vX.Y.Z` запускает сборку установщиков и полный workflow проверок сервера/клиента. После успешных проверок CI публикует выпуск с четырьмя установщиками и общим `SHA256SUMS.txt`. Версия приложения, строка версии в настройках и Windows Setup берётся из тега. Пререлиз `vX.Y.Z-rc.N` сохраняет суффикс в приложении и описании; нативные числовые метаданные используют X.Y.Z.

Домашний runtime публикуется отдельно в `space-server`; там также используются независимые теги `vX.Y.Z`.

Перед тегом перенесите готовые пункты из `Unreleased` в одноимённый раздел `## vX.Y.Z` корневого `Changelog.md` и закоммитьте его. Проверка описания выполняется до сборки. `packaging/release-notes.py` переносит только содержимое этого раздела; пропуск, пустой или дублированный раздел прекращает публикацию. Ручные запуски и обычные изменения main сохраняют артефакты без публикации. Публикация сначала создаёт черновик и переводит его в публичный выпуск после загрузки полного набора файлов. Повторный запуск продолжает черновик; существующий публичный выпуск не перезаписывается. Теги с суффиксом отмечаются как prerelease, обычные — как релизы.

В приложении закреплён дескриптор домашнего runtime (`client/assets/home/runtime-manifest.json`). После публикации нового комплекта выполните `python packaging/pin-home-runtime.py vX.Y.Z`: скрипт проверяет опубликованные JSON и SHA-256 архивов по метаданным GitHub, затем обновляет закреплённый файл. Проверьте diff и только затем выпускайте приложение. Пользовательская база остаётся в отдельном каталоге; переход на другую основную версию PostgreSQL требует отдельной процедуры миграции.

Пример выпуска после подготовки changelog (замените версию на нужную):

```powershell
git tag -a v0.3.0 -m "Space v0.3.0"
git push origin v0.3.0
```

Проверка в настройках приложения читает только публичные релизы space-app с полным набором установщиков. Она не отправляет ключи и токены пространств. Описание изменений можно раскрыть в настройках, выбранный выпуск открывается на GitHub.
