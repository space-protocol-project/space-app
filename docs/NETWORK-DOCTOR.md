# Диагностика сети

В «Эфире» блок «Диагностика подключения» использует тот же код, что и `space-server doctor`. Требуется runtime с `networkDoctorVersion: 2`; опубликованный v0.3.2 этой возможности ещё не содержит. Старый runtime получает предложение обновиться, без попытки запуска неизвестной команды.

Проверка читает конфигурацию, сертификат и публичный server ID, затем проверяет локальный слушатель и каждый объявленный адрес. Проверяются закреплённый SHA-256 сертификата, срок его действия, идентичность сервера и подпись объявления адресов. Перенаправления HTTP не выполняются. База данных, настройки, файрвол и проброс портов не изменяются.

Локальный запуск:

```powershell
space-server doctor -home-data 'C:\Space\data'
space-server doctor -home-data 'C:\Space\data' -wan-ip 100.64.1.2 -json
```

`home-data` — каталог `data` пространства; конфигурация находится рядом с ним. WAN IP вводится вручную со страницы состояния роутера, необязателен и не сохраняется. Диапазон 100.64.0.0/10 указывает на возможный CGNAT; частный IPv4 — на возможный двойной NAT или CGNAT. Частный IPv6 не считается доказательством CGNAT. Публичный IP и успешное подключение из домашней сети не доказывают доступность из интернета.

Для проверки из другой сети панель копирует команду с адресами, SHA-256 сертификата и server ID. Она не содержит секретов владельца. Запустить её следует на другом компьютере вне домашней сети:

```powershell
space-server doctor -endpoint 'https://space.example.org:9443' -fingerprint <SHA256> -server-id <SERVER_ID>
```

Можно повторить `-endpoint` до восьми раз, в том числе с IPv6 в квадратных скобках. Отчёт описывает доступность с компьютера, на котором выполняется команда. В этом режиме без каталога домашнего сервера нет локальных сведений о внешних подключениях: поле `external` остаётся `unverified`.

## Автоматическое внешнее наблюдение без VPS

Публичный HTTPS-вход фиксирует успешные запросы discovery из другой публичной сети. Запущенный Space проверяет сохранённые пространства примерно раз в 20 секунд; поэтому достаточно открыть его на устройстве через другую сеть, например мобильный интернет. Новых запросов с секретами или правами администратора для этого не требуется. Запрос не обязан принадлежать участнику: успешный входящий HTTPS сам по себе доказывает, что запрос пришёл к этому слушателю извне. Личность проверяющего не утверждается.

`doctor -home-data ...` автоматически читает это наблюдение. При свежем результате возвращаются `external: "observed"`, `external_checked_at_unix_ms` и проверки `external_observed` для наблюдавшихся адресов. «Эфир» показывает время последнего подтверждения. На момент проверки результат должен быть не старше 90 секунд. Это историческое наблюдение, а не непрерывный статус.

Учитывается только фактический TCP peer завершённого TLS-сеанса и успешный ответ discovery. Частные, loopback, CGNAT, зарезервированные и переходные IP исключены. Собственные адреса и соседние IPv4 /24 или IPv6 /48 исключены консервативно. Host/SNI должны соответствовать настроенному адресу, а DNS этого адреса должен содержать публичный IP. При неизвестном DNS подтверждения нет. `Forwarded`, `X-Forwarded-For`, `X-Real-IP` и `Via` не используются как доказательство; такие запросы вообще не учитываются. За прокси, relay, VPN или одним CGNAT результат может оставаться неизвестным.

Сведения хранятся в краткоживущем `data/network-witness.json`: server ID, TLS-отпечаток, хеш списка адресов и время/адрес наблюдения. IP проверяющего, токен и личность не записываются. Файл создаётся с закрытыми правами и заменяется атомарно, не чаще раза в 10 секунд. При запуске старый результат сбрасывается, при остановке удаляется. Смена сертификата или списка адресов делает его непригодным; время из будущего и просроченное время отклоняются.

**Граница проверки:** это автоматическое подтверждение входящего внешнего HTTPS, а не независимый активный пробник DNS и NAT-порта. Host/SNI сообщаются клиентом, поэтому одного наблюдения недостаточно для независимой аттестации публичного домена или конкретного проброса порта. Для такой проверки запустите команду на внешнем компьютере. Отдельный постоянно доступный пробник потребует внешнего хостинга; без внешних запросов первый запуск остаётся `unverified`, а не «недоступен».

Каждый маршрут ограничен тремя секундами, команда — 35 секундами. Ответ discovery и вывод subprocess ограничены 16 КиБ. Код завершения 0 означает, что отчёт сформирован; состояние отдельных проверок находится в `checks`. Ошибки параметров возвращают ненулевой код.

Проверки: Go-тесты настоящего TLS/discovery, неверного отпечатка, server ID, подписи и перенаправления; Flutter-тесты отчёта, события, локализации и узкого экрана; `client/tool/home_endpoints_drill.dart` проверяет doctor на одноразовом настоящем пространстве вместе с переключением адресов и MLS.

Предыдущая локальная проверка 16 октября 2026 года: `go test ./...`, `go vet ./...`, `flutter analyze`, Windows release и настоящий endpoint/MLS drill прошли. Последовательный `flutter test --concurrency=1`: 380 пройдено, 8 пропущено. Локальный Go race-прогон недоступен без CGO-компилятора. Автоматическое внешнее наблюдение дополнено тестами давности, идентичности, адресов, прокси и Linux netns; лабораторная сеть не заменяет физическую проверку через провайдера.

Автоматическое наблюдение подтверждено [CI с изолированными сетями](https://github.com/space-protocol-project/space-server/actions/runs/38839711434): рабочий HTTP-обработчик получает настоящий TLS-запрос из другой сети; локальный запрос и поддельный Forwarded не дают подтверждения. [CI runtime трёх ОС](https://github.com/space-protocol-project/space-server/actions/runs/38838947534) проверил запуск, перезапуск, TLS/MLS, обновление и восстановление. Профильные 12 Flutter-тестов, анализ и локальная сборка Windows прошли. Это проверка кандидата, не новый опубликованный релиз.
