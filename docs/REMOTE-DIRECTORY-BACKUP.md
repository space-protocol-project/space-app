# Удалённые копии каталога и внешний свидетель v1

Статус: контракт реализации 0.8.0; результаты проверок будут добавлены после CI.
Контейнер и состав данных остаются [каталогом v1](DIRECTORY-BACKUP.md).
Сборки, генерация и проверки выполняются только в GitHub CI.

## Модель угроз

Хранилище получает только зашифрованный `.spacebackup`, случайный ID цепочки,
ревизию, отпечатки манифеста и контейнера. Свидетель получает только эти
метаданные. Пароль, DEK, адреса пространств и рабочие ключи им не передаются.
Размеры, время запросов и связь с учётной записью при создании видны оператору.

Злоумышленник может подменять, удалять и возвращать старые контейнеры, прерывать
загрузку, повторять запросы и создавать конкурентные обновления. Шифрование
проверяет содержимое; внешний свидетель обнаруживает откат хранилища.
Он должен работать у независимого оператора, с отдельной БД и резервированием.
Разные HTTPS origins проверяются клиентом, но не доказывают независимость.
Компрометация обоих операторов после потери всех локальных отметок может
скрыть откат. Свидетель не доказывает существование ещё не опубликованной копии.
Свидетель доверен сохранять монотонное состояние: откат его собственной БД
нарушает это предположение. Свежая подпись доказывает текущий ответ сервера,
но не заменяет независимое резервирование и контроль восстановления его БД.

Создание цепочки требует действующей сессии незаблокированного участника на
каждом сервере и ограничено личной квотой. Это не выдача device grant и не
операция root. Чтение после потери устройств использует отдельную
случайную 256-битную capability; запись — другую capability. В БД хранятся
только SHA-256 capability. Владение read capability не даёт запись или доступ
к пространствам; владение write capability позволяет испортить будущую цепочку,
поэтому комплект восстановления — секрет. Пароль хранится отдельно.

Владелец с действующей сессией может отозвать слот на каждом сервере. Отзыв
идемпотентен, закрывает обе capability и не позволяет заново занять тот же ID.
При частичном отказе повторяют отзыв; локальный комплект очищается только после
подтверждения обоих серверов. Контейнеры не удаляются и продолжают занимать квоту.
Отзыв grant устройства сам по себе не отзывает отдельно сохранённый комплект.

## Комплект восстановления

Версионный JSON содержит случайный ID, HTTPS origin хранилища и свидетеля,
закреплённые TLS fingerprints и публичные Ed25519-ключи серверов, независимые
read/write capabilities. Это не recovery-карточка личности. Комплект сохраняют
вне всех сопряжённых устройств; автоматического поиска по имени/почте нет.
Потеря комплекта и всех устройств означает потерю locator. Пароль в JSON
не включается. Рабочие session tokens используются только при создании и отзыве.

У цепочки один публикатор; автоматическое согласование нескольких публикаторов
не входит в v1. Перед публикацией на другом устройстве сначала восстанавливают
последнюю подтверждённую копию. Для всей цепочки используют один пароль:
следующая публикация сначала расшифровывает предыдущую. Смена пароля требует
нового комплекта/цепочки; скрытой смены пароля в середине истории нет.

## Публикация и сбои

1. Прочитать актуальную голову свидетеля по свежему случайному challenge.
   Подпись сервера связывает challenge, ID и все поля головы; старый ответ
   не подходит новому запросу. Проверяется закреплённый ключ, не discovery.
2. Создать следующий манифест с ревизией `N+1` и parent последней головы.
   Зашифровать и полностью прочитать обратно до сети.
3. Атомарно сохранить неизменяемый контейнер в хранилище, затем скачать его
   и проверить SHA-256 точных байтов. Прежние версии не удаляются.
4. Обновить свидетель сравнением ожидаемой головы: только `N → N+1`,
   parent должен совпадать. Та же запись повторяется идемпотентно; другая
   запись той же ревизии и пропуск ревизии отклоняются.
5. Проверить свежую подписанную голову и только затем зафиксировать локальный
   экспорт. Между двумя серверами нет общей транзакции. Сбой до шага 4 оставляет
   непубличную новую копию; повтор должен завершать именно её, а не создавать
   иной ciphertext той же ревизии. Незавершённая публикация сохраняется локально.

Если утрачен и локальный журнал, отдельная команда ищет контейнер `N+1` при
подтверждённой голове `N`. Клиент расшифровывает его, проверяет parent и доверие,
показывает состав и признак отсутствующего подтверждения свидетеля. Только после
явного подтверждения и повторного ввода пароля сохраняется новый локальный журнал
с теми же байтами и завершается публикация. Настройки не применяются этой командой.
Если `N>0`, сначала нужно применить подтверждённую копию `N`. Изменение головы
свидетеля или локального плана между просмотром и подтверждением блокирует шаг.

Оба сервера ограничивают размер и количество цепочек/версий. Нет фонового
удаления, перезаписи контейнеров или бесконечного накопления. Исчерпание квоты
показывается ошибкой; retention остаётся отдельной задачей.
Пределы v1: 5 МиБ на контейнер, 32 версии на цепочку, 4 слота на участника,
64 слота и 256 МиБ контейнеров на сервер, не более 64 МиБ на участника.
Отозванные слоты и их контейнеры также учитываются.

## Восстановление

Импортировать комплект, отдельно ввести пароль, получить свежий подписанный
ответ свидетеля и скачать указанную им ревизию. Проверить ID, ревизию, parent,
SHA-256 контейнера, аутентификацию архива и digest манифеста. После скачивания
повторно проверить голову: конкурентное обновление требует нового preview.
Недоступность свидетеля, неверная подпись, откат относительно локальной головы,
расхождение и отсутствие контейнера блокируют этот сценарий. Автоматического
перехода на старую копию нет. Ручное открытие отдельного локального файла остаётся
явно непроверенным на новизну, если нет локальных отметок.

Затем действуют обычные preview, проверка pins/личности, отдельное подтверждение,
выбор замены настроек и защищённый журнал. Подписки возвращаются отдельно через
серверные права. Каталог не возвращает полномочия: нужны pairing/recovery.
Перед применением удалённая голова проверяется ещё раз. Отказ сети не должен
незаметно разрешать применение старого preview.

Локальные файлы и удалённый комплект имеют независимые цепочки: сохранение
файла не продвигает голову свидетеля. При смене TLS-сертификата либо ключа
сервера комплект обновляют по доверенному каналу; автоматической замены
закреплений нет. Подтверждение новизны относится к моменту последнего ответа
свидетеля: другая публикация может произойти сразу после него.

Разделение целостности, отката и заморозки согласуется с
[моделью TUF](https://theupdateframework.github.io/specification/v1.0.36/).
Это отдельный протокол Space, не реализация TUF и не заявление об аудите.
