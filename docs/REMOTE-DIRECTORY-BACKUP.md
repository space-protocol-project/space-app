# Зашифрованные копии на сервере пространства

## Компоненты

В Space есть приложение, сервер пространства и runtime для запуска этого же
сервера из приложения. Хранение резервных копий — функция сервера пространства.
Новых типов серверов, отдельного хранилища, внешнего свидетеля или обязательного
общего сервиса нет. Сервер выбранного пространства может работать самостоятельно
либо запускаться приложением через runtime. Файловый экспорт также сохраняется.

В настройках приложения выбирают одно уже подключённое пространство.
Для работы с локальным runtime используется существующее проверенное соединение;
создание клиента резервных копий и его закрытие не закрывают сессию пространства.
С другого устройства используется HTTPS-адрес пространства из комплекта.

## Модель угроз

Приложение шифрует каталог до отправки. Сервер получает только случайный ID,
ревизию, ciphertext, его SHA-256 и хеш внешней цепочки. Пароль, DEK, отпечаток
открытого манифеста, рабочие ключи, MLS, история и вложения не передаются.
Размеры, время запросов и личность при создании слота видны серверу пространства.
Контейнер v1 и состав манифеста v2 описаны в [формате каталога](DIRECTORY-BACKUP.md).
Ревизии настроек находятся внутри ciphertext и не меняют серверный API.

Подмена ciphertext обнаруживается по хешу и AES-GCM. Подписанный свежий ответ
с challenge подтверждает текущее сообщение выбранного сервера, но не делает
этот сервер независимым источником новизны. Известный локально откат или
ветвление блокируются. После потери всех локальных отметок старую корректную
копию нельзя гарантированно отличить от последней, если сам сервер откатился
или сообщил старое состояние. Время файла не считается доказательством новизны.
Эта граница показывается в интерфейсе и не скрывается за словом «проверено».

## Доступ и комплект восстановления

Создание слота требует действующей сессии незаблокированного участника.
Отзыв доступен владельцу с действующей сессией. Чтение и запись используют
разные случайные 256-битные capability; в БД хранятся только их SHA-256.
Они не являются device grants и не дают доступа к чатам или управлению root.

`.spacebackupkit` — строгий JSON до 8 КиБ: v=1, kind=space.remote-backup,
случайный 16-байтный id и один объект space с origin, TLS fingerprint,
Ed25519-ключом сервера и read/write capability. Секретный комплект сохраняют
вне устройства, отдельно от пароля. Рабочие session tokens и пароль в него
не входят. Неизвестные поля и прежний формат с двумя адресами отвергаются.
Смена сертификата/ключа требует обновления закрепления доверенным способом.

Каталог не восстанавливает полномочия участника: для этого отдельно нужны
сопряжение, recovery-карточка либо другое устройство. Подписки применяются
отдельно после входа той же личности через серверные ACL и expected_revision.

## Запись и повтор после сбоя

1. Прочитать подписанную голову выбранного пространства со свежим challenge.
2. Проверить её против локальной истории. Для существующей цепочки открыть
   предыдущий контейнер тем же паролем и получить parent открытого манифеста.
3. Создать следующую версию, зашифровать и полностью проверить её локально.
   Сохранить в защищённом журнале точные ciphertext и внешнюю голову.
4. Передать контейнер серверу пространства. Одна транзакция PostgreSQL сохраняет
   неизменяемую версию и продвигает текущую голову N → N+1. Повтор тех же байтов
   идемпотентен; другая версия с тем же номером и пропуск номера отклоняются.
5. Скачать версию, проверить hash/AEAD и повторно получить подписанную голову.
   Только после этого зафиксировать локальный экспорт и очистить журнал.

Если ответ потерян после commit, версия и голова уже доступны вместе. Повтор
использует тот же журнал. После потери исходного устройства новый профиль
может сразу открыть сохранённую копию по комплекту и паролю: отдельного шага
подтверждения на другом сервере нет. Явное успешное применение проверенной
версии очищает покрытую ею старую локальную очередь публикации.

Одна цепочка использует один пароль и одного публикатора. Смена пароля требует
новой цепочки. Файловые копии имеют отдельную цепочку и не мешают сохранению
копий на пространстве. В разрабатываемой схеме 46 пределы составляют 5 МиБ на
контейнер, 256 версий, 4 слота и 512 МиБ на участника, 64 слота и 2 ГиБ на
сервер. Отозванные данные учитываются. Условия подтверждения и очистки описаны
в [политике хранения](REMOTE-BACKUP-RETENTION.md); её проверки ещё не завершены.

## Восстановление

На чистом профиле открыть комплект, ввести пароль, проверить подписанный ответ,
контейнер, структуру, pins и личность. Предварительная проверка ничего не меняет.
Серверная версия показывается с оговоркой о локальных отметках новизны.
Применение требует отдельного подтверждения; настройки по умолчанию сохраняются.
Непосредственно перед применением голова проверяется повторно. Недоступность,
подмена, изменение версии и конфликт доверия блокируют этот шаг.

Сохранять файловые копии отдельно от данных сервера пространства полезно:
потеря сервера вместе с его единственной копией не устраняется шифрованием.

## Внешняя цепочка и подписанный ответ

Все hash — SHA-256, канонический base64url без padding. Внешний parent — digest
предыдущей головы. digest — hash UTF-8 строк, соединённых LF без завершающего LF:

```text
space/backup-chain/v1
id
revision
parent
archive_digest
```

archive_digest — hash точных байтов контейнера. Внутренний parent манифеста
содержит отпечаток открытого текста и остаётся зашифрованным.
Сервер и клиент проверяют внешнюю цепочку. Ed25519 подписывает строки:

```text
space/backup-head/v1
challenge
id
revision
digest
parent
archive_digest
```

Challenge — 32 случайных байта. Пустая голова имеет revision=0 и пустые hash.
Подписанный ответ относится к серверу пространства, не к отдельной службе.

## Миграция и проверки

Схема 45 удаляет исключённую роль свидетеля и её записи, не содержавшие
контейнеров. Зашифрованные версии, головы пространства и идентичность сервера
сохраняются. Прежние RPC отдельного свидетеля удалены, совместимых адаптеров нет.
[GitHub CI](https://github.com/space-protocol-project/space-app/actions/runs/40553570029)
прошёл: 131 целевой тест и два штатных пропуска, анализ приложения и собственных
пакетов без замечаний, COG ≤15, полный Go-прогон с гонками, vet, проверкой
модулей и уязвимостей. Проверены миграция с сохранением копий, атомарная запись,
конкурентное обновление, квоты и отзыв. Сквозной сценарий использует ровно один
сервер пространства и одну схему PostgreSQL: потерянный ответ после commit,
перезапуск, восстановление без старой сессии и сохранение действующей сессии
при закрытии клиента копий. Нативный Linux проверил расшифрование, просмотр,
применение и горячий перезапуск.
Системное хранилище Windows DPAPI проверено отдельным
[аварийным сценарием](DIRECTORY-CRASH-RECOVERY.md): 19 проверок, 14 принудительных
завершений и холодное восстановление каталога с сохранением прежних данных.
По решению пользователя приёмка на физических устройствах и независимая
экспертиза исключены из условий milestone; выполненными они не считаются.
