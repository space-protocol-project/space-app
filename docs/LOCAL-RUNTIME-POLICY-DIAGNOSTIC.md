# Диагностика отказа запуска тестового runtime

Дата: 18 октября 2026 года. Репозиторий: `space-app`. Android не использовался.

## Подтверждённые факты

- Запрос отклонён инструментом исполнения до создания процесса: `CreateProcess … Rejected … blocked by policy`. Это не сообщение самого runtime.
- Сборка собственного runtime, запуск и штатная остановка локальной тестовой PostgreSQL проходили.
- Метаданные текущего чата и журналы Codex показывают `approval_mode=never`, отключённый sandbox / `DangerFullAccess`. Поэтому нельзя приписывать отказ обычному запросу Auto-review на выход из sandbox.
- В пользовательском `~/.codex/rules/default.rules` находятся только два разрешения чтения для другого проекта. Правила запрета runtime там нет. Диагностический `codex execpolicy check` для запуска через PowerShell не нашёл совпавших правил (`matchedRules: []`); проверка команду не исполняла. Это результат проверки указанного локального файла, а не всех внутренних политик среды.
- Пользовательский `~/.codex/hooks.json` содержит только `SessionStart`; блокирующего `PreToolUse` / `PermissionRequest` в нём нет.
- В проверенных локальных конфигурациях нет настройки `guardian_policy_config` или пользовательского переопределения Auto-review.
- В журнале текущего чата, его сохранённой истории, журнале Windows sandbox и журналах desktop-приложения не найдено отдельного решения с именем правила или причиной именно этого отказа. В истории сохранён общий текст `blocked by policy`.
- Установленный CLI: `0.163.0-alpha.10.2`. Метаданные создания текущего чата содержат `0.162.0-alpha.17.2`; это не доказывает, что старый исполняемый файл обслуживает текущие команды.

## Какое действие требуется разрешить

Запуск собственного `space-server.exe`, собранного из соседнего `space-server`, в каталоге `.local/space_ui_32c08dc82b934536b31870af99919560/`.

- HTTP: `127.0.0.1:18086`.
- gRPC: `127.0.0.1:18087`.
- Origin: `http://127.0.0.1:18086`.
- PostgreSQL: отдельная локальная тестовая база на `127.0.0.1:59465`, схема `space_ui_32c08dc82b934536b31870af99919560`.
- Журналы: `stdout.log` и `stderr.log` в том же тестовом каталоге.
- Окно процесса скрыто. Автозапуска, службы, правила файрвола, изменения публичного доступа и обращения к пользовательскому серверу не требуется.
- После проверки процесс и тестовая PostgreSQL должны быть остановлены, ненужная сборка удалена; ключи и базы пользователя не затрагиваются.

## Вывод и дальнейшее действие

Точный идентификатор блокирующей политики **не установлен**. Проверенные пользовательские правила и hooks его не объясняют. Обоснованно менять локальную защиту или объявлять это ошибкой Windows/антивируса нельзя.

Нужно получить полное решение механизма, вернувшего отказ, и воспользоваться его штатным одобрением конкретного действия, если оно предусмотрено. Обычное сообщение пользователя «продолжи» не является подтверждением того, что среда зарегистрировала техническое одобрение. В доступных инструментах этой сессии такого механизма не обнаружено.

Официальная документация описывает `/approve` для выбора отклонённого действия в **CLI TUI**: <https://learn.chatgpt.com/docs/sandboxing/auto-review>. Это не доказательство применимости команды к данному отказу в desktop-чате с `approval_mode=never`.

Если решение не доступно через интерфейс, этот отчёт можно приложить к обращению через штатную обратную связь Codex. Не прикладывайте `auth.json`, ключи, базы или полный пользовательский профиль.

Проверка установленных обычного и MLS-чата и фактического нажатия системного уведомления остаётся открытой. Ранее прошедший 61 автоматический тест не заменяет её. Повторно запускать одни и те же проверки без изменения блокирующего условия не требуется.
