# Восстановление домашнего сервера

Сначала штатно остановите домашний сервер. Не удаляйте `postmaster.pid`,
журнал обновления или исходные данные, чтобы снять блокировку запуска.
Если остановка не подтверждена, не копируйте каталог работающей PostgreSQL.

## Что показывает приложение

- Незавершённая исправная операция: «Продолжить обновление или восстановление».
- Повреждённый/недоступный журнал, в том числе один оставшийся `.tmp`: автоматическое продолжение заблокировано.
- Отсутствующая копия: нужен прежний каталог копии либо другой подтверждённый способ восстановления.
- Повреждённая/неполная копия: до восстановления проверяются платформа, состав файлов и SHA-256; текущие данные не заменяются.
- Повреждённая контрольная запись или неоднозначные каталоги: нельзя подтвердить исходную идентичность/схему, переключение заблокировано.

Нажмите «Скопировать сведения»: это каталог, код ошибки и доступные метаданные
операции; пароли, ключи и содержимое базы в сведения не включаются.
После исправления внешней причины снова откройте панель; журнал не редактируйте
наугад. Полная проверка SHA-256 копии выполняется при продолжении восстановления
и повторном открытии панели после ошибки копии. При обычном запуске панели
без этой ошибки всю копию повторно не читают.

Для переноса на другой компьютер используйте [экспорт и импорт пространства](SPACE-TRANSFER.md).
Копирование физического каталога ниже предназначено для восстановления
исходной установки при сбое обновления.

## Сохранить исходное состояние

После подтверждённой остановки сохраните целиком каталог `home-server`,
указанный в сведениях: `data`, `runtimes`, `active-runtime.json`, `config.json`,
`update-operation.json` и его `.tmp`, `update-…-baseline.json`, `backups`,
`recoveries`, `failed-data`. Не публикуйте эту копию или её содержимое:
там находятся серверные ключи и пароль PostgreSQL. Сохраните доступ только
владельцу; заранее проверьте место для ещё одного объёма данных.

До миграций отмена подготовки оставляет прежний runtime выбранным.
После начала миграций возврат одного исполняемого файла недостаточен:
нужна согласованная резервная копия прежней схемы. `failed-data` сохраняет
изменённую базу отдельно; автоматически очищать его нельзя.

## Исправный журнал и копия

Используйте кнопку продолжения. Восстановление сначала создаёт новый каталог
`recoveries/<id>`, проверяет прежние server ID, TLS и схему, затем переносит
нынешнюю базу в `failed-data/<id>` и переключает восстановленные данные.
Повторный запуск после прерывания между этими переносами продолжает ту же
операцию. Старый runtime активируется только после проверки результата.

Если копия была перемещена на другой диск, верните подтверждённую копию той же
операции в ожидаемый `backups/<id>`, сохранив манифест и весь состав файлов.
Не подставляйте копию другой операции: её схема и идентичность могут отличаться.

## Ручная подготовка при повреждённом журнале

После сохранения исходного состояния можно подготовить копию отдельно,
не заменяя существующую установку. Выберите проверенный runtime той же
платформы и PostgreSQL 17, поддерживающий `-home-restore` и `-home-check`.
Команды ниже предназначены для Windows PowerShell; пути заменяет владелец:

```powershell
$runtimeDirectory = 'C:\путь\home-server\runtimes\проверенный-runtime'
$backupDirectory = 'C:\путь\home-server\backups\update-идентификатор'
$restoreDirectory = 'C:\путь\home-server-manual-restore'
& "$runtimeDirectory\space-server.exe" -home-runtime $runtimeDirectory -home-restore $backupDirectory -home-restore-to $restoreDirectory
if ($LASTEXITCODE -ne 0) { throw 'Копия не восстановлена; исходные данные не заменять' }
& "$runtimeDirectory\space-server.exe" -home-runtime $runtimeDirectory -home-data "$restoreDirectory\data" -home-check
if ($LASTEXITCODE -ne 0) { throw 'Восстановленные данные не прошли проверку' }
```

Каталог назначения должен отсутствовать. Сервер проверяет копию, создаёт
новый каталог и проверяет чистую остановку PostgreSQL. `-home-check` открывает
только локальную базу для проверки, не выполняет миграции и закрывает её;
внешние HTTP/gRPC порты не открываются.

Сверьте server ID, TLS-отпечаток, основную версию PostgreSQL и схему с известным
исходным состоянием. Восстановленные `config.json` и `active-runtime.json`
относятся к прежней версии; для отдельного восстановленного корня нужен и
проверенный каталог этого прежнего runtime. Если идентичность/схему подтвердить
невозможно или копии нет, не переключайте установку — автоматического обхода
блокировки нет.

Переключение повреждённой установки выполняется отдельно после проверки:
закрыть Space, подтвердить отсутствие серверных процессов и удерживать
блокировку запуска, сохранить прежний корень под другим именем и только затем
поместить полностью проверенный восстановленный корень на его место. Ничего
не удаляйте из сохранённого корня. Новый журнал из обрывков не собирайте.
После запуска отдельно проверьте сообщения, владельца/участников и приглашения.

На macOS/Linux команды аналогичны с `space-server` вместо `.exe`; перенос
между ОС/архитектурами и смена основной версии PostgreSQL этим способом
не поддерживаются.

## Права Windows и границы проверки

Начиная с runtime v0.2.2 временный каталог копии получает защищённую DACL
до записи данных: доступ владельцу процесса и SYSTEM, без наследования
доступа других пользователей. Файлы наследуют эти ограниченные права.
То же правило применяется к новому каталогу восстановления.
[Механизм Windows](https://learn.microsoft.com/en-us/windows/win32/secauthz/automatic-propagation-of-inheritable-aces).

Изменение опубликовано в runtime v0.2.2 и закреплено в приложении v0.2.2. Права уже созданных копий автоматически не переписываются.
