# Постоянная очередь локальных вложений

Продолжение v0.4 после проверки двух устройств. Реализация для обычных каналов; серверный контракт и схема PostgreSQL 18 не меняются, подходит runtime v0.3.6.

## Поведение

После нажатия «Отправить» выбранные файлы копируются в зашифрованное локальное хранилище, затем сообщение записывается в постоянную очередь. Поле и список выбранных файлов очищаются только после сохранения. Исходные файлы после этого можно переместить или удалить. Черновики до нажатия «Отправить» этим механизмом не сохраняются.

Выбор файлов доступен без сети по ранее сохранённым разрешениям и политике вложений. Старые записи истории без сохранённой политики требуют успешного подключения. Запрет вложений скрывает выбор и перетаскивание для соответствующего пространства; сервер повторно проверяет разрешения при загрузке. Закрытые MLS-каналы сохраняют отдельный механизм зашифрованной отправки.

Ограничения: 20 МиБ на файл, пять файлов на сообщение, 200 МиБ зашифрованных копий на пространство и выдачу устройства. Общая очередь по-прежнему ограничена 100 сообщениями и 1 МиБ метаданных. Переполнение не вытесняет ожидающие сообщения.

## Хранение и восстановление

- На диске — AES-256-GCM с независимыми случайными nonce. Ключ хранится в системном защищённом хранилище; имена и SHA-256 файлов входят в защищённые метаданные очереди. AAD связывает копию с server/principal/grant и описанием файла. Исходный путь не сохраняется.
- Имя файла на диске — SHA-256 ключа сообщения и номера вложения. Валидатор очереди запрещает ссылку на копию другого сообщения. Чтение проверяет размер, AEAD и SHA-256; отсутствующий или повреждённый ключ не заменяется автоматически.
- Запись проходит через временный файл, flush и rename. Блокировка между процессами охватывает подготовку копий и запись метаданных. Очистка оставшихся после аварии файлов сверяет ссылки очереди под той же блокировкой; при ошибке чтения метаданных ничего не удаляется. Неудачная подготовка набора откатывает созданные ею копии.
- BeginUpload использует прежний ключ загрузки и подтверждённое сервером смещение. Потерянный ответ на часть не требует начинать файл заново. Проверяются имя, размер, хеш, ID завершённого файла и смещения.
- Готовые ID сохраняются до CreateContent. После потерянного подтверждения сообщения повторяется прежний CreateContent без новой загрузки. Если неиспользованный файл истёк на сервере до создания сообщения, полностью локальное вложение восстанавливается из копии. Для старых запросов только с ID без локальной копии такое восстановление невозможно.
- Подтверждённое сообщение сначала сохраняется в истории, затем удаляется из очереди; после этого удаляются локальные копии. Ошибка очистки копии не повторяет уже подтверждённое сообщение. При завершении процесса очистка ожидается ограниченное время.
- Явная отмена убирает запись и копии; активная загрузка отменяется по возможности. Ранее завершённые неиспользованные серверные файлы могут оставаться до штатного истечения через 24 часа. Отмена не удаляет сообщение, которое сервер уже принял.
- Явная очистка локальных данных убирает копии и их ключ соответствующей области. Отзыв доступа останавливает отправку, но не стирает сохранённую очередь. Перенос на новый grant требует отдельного подтверждения доверия и в этот срез не входит.

Приложение в закрытом состоянии не отправляет данные. Возобновление выполняется после запуска и подключения. Обычные файлы остаются обычными файлами для сервера; локальное шифрование очереди не превращает канал в E2EE.

## Проверки

`client/test/queued_files_test.dart`: шифрование, повреждение, привязка к области и имени, потеря ключа, ограничения, параллельные экземпляры, откат набора и очистка аварийных копий. Проверяются частичная загрузка с потерянным ответом, неоднозначная запись, отсутствие исходника, истёкший серверный файл, запрет политики и отмена. Интерфейс проверяется на 390 px и масштабе текста 150% в ru/zh/en.

`client/test/live/persistent_files.dart` включён в серверную сквозную проверку. Настоящие ConnectRPC/PostgreSQL, сохранённая часть с потерянным ответом, удалённый исходник, два перезапуска и потерянное подтверждение сообщения. Второй клиент получает ровно одно сообщение и исходные байты. Сценарий воспроизводится через `tools/check_attachments.ps1` и выполняется в CI, когда выбран соответствующий коммит приложения.

`client/tool/native_vault_drill.dart` проверяет ключ и зашифрованную копию между настоящими процессами Windows, вместе с прежними проверками ключей, избранного, журнала и прерванной атомарной записи. Используется отдельный случайный тестовый слот.

Физический Android по просьбе пользователя не используется. Приёмка принудительного завершения мобильного процесса остаётся отдельным пунктом.

Локальная проверка 16 октября 2026: полный набор — 444 успешных теста и 8 штатных пропусков; после исправления перенаправления AppData в Windows повторно прошли 56 профильных тестов и сквозной сценарий с PostgreSQL. Анализ без замечаний, максимум COG 15 без превышений. Настоящие процессы Windows подтвердили сохранность ключа и копии файла, восстановление после аварийной записи и очистку отдельного тестового слота. Эти изменения пока не выпущены.
