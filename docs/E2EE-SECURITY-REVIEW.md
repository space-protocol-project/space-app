# Проверка безопасности E2EE перед экспериментальным выпуском

Дата: 15 октября 2026 года. Проверены рабочие копии space-app, space-server и контракт space-protocol. Это внутренняя проверка исходников и отрицательных сценариев, а не независимый криптоаудит.

Дополнение от 16 октября: [восстановление без ratchet, автоматическое обслуживание, self-update, код группы, бюджеты и mls-rs](E2EE-HARDENING.md). Оно уточняет перечисленные ниже ограничения первоначальной проверки.

## Граница защиты

Закрытые MLS-каналы используют OpenMLS 0.9.1. Сервер получает ciphertext сообщений и файлов; ключи файлов, исходные имена и текст передаются внутри MLS. Открытые каналы остаются открытыми. Первичное доверие требует независимой сверки отпечатков устройств: регистрация ключа на сервере сама по себе не подтверждает личность.

Проверены привязка signing key к устройству, Welcome/Commit, авторство, управление составом, root-цепочка и сохранение устройств, повторная доставка, checkpoint/outbox, файловый AEAD, запрет открытых Content RPC, серверные ACL и лимиты. Расшифрованная история и ключи файлов сохраняются в защищённом хранилище клиента; пользовательский экспорт файла создаёт обычный открытый файл в выбранном месте.

## Найдено и исправлено

| Проблема | Последствия | Исправление и проверка |
| --- | --- | --- |
| Состав в ответе на собственный Commit принимался от сервера | Рассогласование локального списка устройств и криптографического состояния группы | До сохранения snapshot Rust сверяет подписанные bindings ответа с фактическим составом OpenMLS. Неверный список отклоняется без изменения snapshot/revision; затем правильное подтверждение успешно |
| Ответ Publish не сравнивался с исходным запросом | Ложное подтверждение могло убрать неподтверждённую операцию из outbox | Сверяются ciphertext, request ID, вид, эпоха, автор и параметры изменения состава/управления. Поддельный сервер в тесте не может очистить очередь; повтор использует прежний пакет |
| Пакеты с собственным grant ID пропускались без проверки | Сервер мог выдать посторонний пакет за собственный и продвинуть курсор | Квитанция SHA-256 связывает подтверждённый собственный пакет с последовательностью и служебными полями. Echo сверяется с сохранённой квитанцией. Неизвестный пакет отклоняется; правильный не дублирует сообщение |
| Не проверялся последовательный порядок событий | Повтор, перестановка или пропуск могли незаметно продвинуть локальный курсор | После вступления принимается только следующий sequence. Первый Welcome может находиться в середине истории. Это локальная проверка порядка, не глобальный журнал прозрачности |
| Клиент накапливал неограниченный ответ RPC до декодирования | Недоверенный сервер мог вызвать чрезмерное потребление памяти | Unary ограничен 8 МиБ, поток — 8 МиБ на кадр. Заголовок кадра проверяется даже при разделении между TCP-частями. Общая длина корректного потока не ограничена этим пределом. Есть проверка настоящим HTTP-сервером |
| Windows-плагин защищённого хранилища обрезал исходный файл перед записью нового | Сбой процесса во время сохранения мог повредить MLS checkpoint и другую защищённую запись | Локальная копия плагина записывает только ciphertext в новый временный файл с CREATE_NEW, проверяет результат WriteFile, вызывает FlushFileBuffers и заменяет запись через MoveFileEx с WRITE_THROUGH. Ошибка сохраняет исходный файл. Отдельный C++-тест проверяет блокировку замены, целостность прежних байтов, повтор после снятия блокировки и отсутствие оставшихся временных файлов после обычной ошибки |
| Android-плагин использовал асинхронный apply и автоматический resetOnError | Возврат из write/readback не гарантировал завершения записи на диск; ошибка могла вызвать сброс ключей | Автосброс отключён. После write/delete приложение ожидает commit зашифрованных данных, обёрнутых ключей и настроек плагина на фоновой очереди Android. Имена хранилищ определяет конфигурация того же плагина. Ошибка commit передаётся вызывающему коду; без подтверждения запись не считается успешной. Проверены Dart-контракт и обработка ошибки; физическое аварийное завершение Android ещё не проверено |
| Устаревшие серверные зависимости и сборочный Go | govulncheck показал 18 известных уязвимостей с найденными путями вызова; это не воспроизведение эксплуатации | Go 1.27.2, gRPC 1.83.2, pgx 5.9.2, x/net 0.60.0, x/text 0.42.0 и совместимые транзитивные обновления. Повторный модульный скан не находит известных уязвимостей |

Проверка опубликованных [уведомлений OpenMLS](https://github.com/openmls/openmls/security/advisories) подтвердила, что используемая 0.9.1 исправляет [неограниченную рекурсию при разборе расширений](https://github.com/openmls/openmls/security/advisories/GHSA-gc79-23g3-8g52). Дополнительная проверка OSV охватывает активные зависимости семи поставляемых Rust-целей, включая build/dev-зависимости. Неиспользуемые optional crates из Cargo.lock и неподдерживаемые платформы не объявляются частью выпуска; скан всего lock отдельно обнаруживал уведомления для таких пакетов.

## Обязательные проверки выпуска

- Публикация приложения по тегу теперь зависит от полного workflow MLS: Rust-тесты и clippy на Windows/Linux/macOS, Android compilation и OSV. Ошибка сети/сканера или найденная запись прерывает проверку.
- Проверка runtime включает закреплённый govulncheck 1.9.0 на уровне модулей. go.mod требует исправленный Go; сборочные workflows читают эту версию.
- Windows-сборка запускает `tools/check_secure_storage.ps1`: компиляция теста того же заголовка, который использует поставляемый плагин, с /W4 /WX. Новый формат зашифрованной записи не вводится.
- Описания экспериментального MLS и требования нового runtime добавлены в Unreleased обоих репозиториев. Релиз и тег этой проверкой не создаются.

Команды воспроизведения:

```powershell
. ./tools/mls_environment.ps1
python tools/check_mls_advisories.py
# Из space-server:
go run golang.org/x/vuln/cmd/govulncheck@v1.9.0 -C cmd/space-server -scan=module
go test ./...
go vet ./...
# Из space-app/client:
flutter analyze
flutter test --concurrency=2
```

## Что эта проверка не гарантирует

- Независимый криптоаудит, совместимость с другой реализацией MLS, ручная приёмка на настоящем Android и macOS/Linux ещё нужны. Сборка APK не заменяет проверку телефона.
- Взлом устройства, извлечение его защищённого хранилища, вредоносное обновление приложения или открытый экспорт могут раскрыть доступную этому устройству историю.
- Смена root сохраняет действующие устройства; она не удаляет скомпрометированный MLS leaf. Для прекращения его доступа необходим Remove/Commit.
- Сервер видит участников, идентификаторы, размеры и время; может отказать в доставке, скрывать изменения или разделить клиентов на разные представления истории. Локальная последовательность и подписи не заменяют внешний журнал прозрачности и независимую проверку ключей.
- Локальная квитанция связывает ответ сервера с отправленным пакетом; она не доказывает сохранение на злонамеренном сервере или получение другим участником. Sequence и время задаются сервером: проверка последовательности не обнаруживает все варианты сокрытия и перенумерации событий.
- Полный согласованный откат локального хранилища не обнаруживается без независимого монотонного якоря. Подтверждение записи/readback не является испытанием внезапного отключения питания на каждой ОС.
- Карточка восстановления root не восстанавливает утраченное MLS-состояние. Перенос/резервирование этого состояния и миграция его формата остаются отдельными задачами.

Итоговые результаты запуска записаны в MLS-CHECKS.md. До выполнения оставшейся приёмки выпуск следует обозначать как экспериментальный.
