# Пространство на Linux-сервере без домашнего компьютера

Начиная с приложения и runtime v0.3.3. Нужен Linux x64 с glibc,
обычный пользователь (не root), `curl`, `unzip`, `sha256sum` и доступный TCP 8443.
Отдельные Go и PostgreSQL не нужны. Участники могут пользоваться Android.

```sh
curl -fsSL https://raw.githubusercontent.com/space-protocol-project/space-server/v0.3.3/packaging/install.sh | sh
```

Установщик скачивает последний runtime, проверяет SHA-256 и запускает сервер.
При первом запуске внешний IP определяется через ipify. Если нужен домен или
другой внешний порт, передайте адрес явно:

```sh
curl -fsSL https://raw.githubusercontent.com/space-protocol-project/space-server/v0.3.3/packaging/install.sh | sh -s -- -address https://space.example.org:9443 -listen 0.0.0.0:9443
```

1. Разрешите входящий TCP-порт в файрволе сервера и в панели провайдера.
2. Дождитесь ссылки настройки в терминале. Она содержит отпечаток сертификата,
   server ID и одноразовый секрет; действует 15 минут. Не публикуйте ссылку.
3. На компьютере или телефоне откройте Space → подключение, вставьте ссылку,
   проверьте сервер и нажмите кнопку подключения. Первый вошедший по этой ссылке
   становится владельцем. Создавать пространство на своём компьютере не нужно.
4. Создайте приглашение для остальных. В управлении пространством → участники
   выберите роль «Администратор» нужному человеку. Администраторов может быть
   несколько; владелец остаётся один. На дополнительном устройстве право управления
   выдаётся отдельно, обычный grant сам по себе не расширяется.

Сервер работает в текущем терминале; Ctrl+C штатно останавливает его.
Повторный запуск той же команды сохраняет владельца, участников, каналы и данные.
После назначения владельца повторная ссылка настройки не выдаётся. Если 15 минут
истекли до первого входа, перезапустите сервер — старая ссылка станет недействительной.

Данные: `~/.local/share/space-server/home/data`; сеть: `home/config.json`.
Runtime хранится отдельно в `runtimes/<версия>`. `SPACE_HOME` меняет общий каталог,
`SPACE_VERSION=v0.3.3` закрепляет версию скачивания. Каталоги старых runtime
установщик не удаляет. Для последующих запусков без скачивания используйте:

```sh
~/.local/share/space-server/runtimes/v0.3.3/space-server start -data ~/.local/share/space-server/home
```

При существующей конфигурации сервер использует сохранённые адреса. Их можно
менять через `home/config.json` при остановленном сервере; поддерживаются несколько
адресов, домен и IPv6. За CGNAT нужен публичный адрес или туннель. Настройка NAT,
контейнерный образ и relay остаются отдельными задачами. Автозапуск описан ниже.

## Постоянная работа на VPS: systemd

Нужен systemd с пользовательским менеджером. Войдите по SSH обычным пользователем;
`su` без пользовательской шины может не подойти. Новый режим установщика совместим
с опубликованным runtime v0.3.3 и новее. Старый установщик из тега v0.3.3 ещё не
знает `--service`, поэтому для этого режима используйте актуальный установщик:

```sh
curl -fsSL https://raw.githubusercontent.com/space-protocol-project/space-server/main/packaging/install.sh | sh -s -- --service
```

Адрес и порт можно передать после `--service`:

```sh
curl -fsSL https://raw.githubusercontent.com/space-protocol-project/space-server/main/packaging/install.sh | sh -s -- --service -address https://space.example.org:9443 -listen 0.0.0.0:9443
```

Установщик включает linger для текущего пользователя — службы работают без
активного входа и запускаются при загрузке. Если политика VPS требует прав
администратора, выполните один раз и повторите установку:

```sh
sudo loginctl enable-linger "$USER"
```

Сам сервер и его PostgreSQL всегда запускаются от обычного пользователя. Root
для них не нужен. Установка создаёт одну службу `space-server.service` для этого
пользователя. Сначала остановите прежний запуск в терминале через Ctrl+C: два
процесса не должны одновременно использовать один каталог базы. Прежние данные
из стандартного каталога сохраняются; если вы задавали `SPACE_HOME`, укажите тот
же абсолютный каталог при установке службы.

После сообщения о готовности можно закрыть SSH и перезагрузить VPS. Внешний
TCP-порт всё равно должен быть открыт; установщик не меняет файрвол провайдера.
Служба перезапускается при аварийном завершении; после пяти быстрых сбоев за
две минуты systemd останавливает повторные попытки — проверьте журнал и причину.

```sh
systemctl --user status space-server
systemctl --user restart space-server
systemctl --user stop space-server
journalctl --user -u space-server -n 50
```

Остановка сначала завершает сервер, давая ему закрыть PostgreSQL; данные остаются.
Для отключения запуска после перезагрузки:

```sh
systemctl --user disable --now space-server
```

Для повторного включения: `systemctl --user enable --now space-server`. Если
достигнут предел повторов, сначала `systemctl --user reset-failed space-server`.

Одноразовая ссылка выводится установщиком и хранится в
`~/.local/share/space-server/setup.txt` с правами 0600; она не попадает в journal.
При `SPACE_HOME` файл находится в указанном каталоге. Если ссылка истекла до
назначения владельца, перезапустите службу и прочитайте новую:

```sh
systemctl --user restart space-server
cat ~/.local/share/space-server/setup.txt
```

Дождитесь готовности сервера перед чтением. После назначения владельца файл
при следующем запуске будет пустым: повторная настройка не нужна. Unit хранится
в `~/.config/systemd/user/space-server.service`, приватный скрипт запуска — в
`~/.local/share/space-server-service/run`.

Повторная установка `--service` проверяет новый runtime до остановки прежней
службы, сохраняет каталог данных и включает запуск снова. Это не резервная копия:
перед обновлением runtime сделайте резервную копию пространства по инструкции
обновления. Для временного запуска в терминале остаётся режим `--foreground`.

Защита первого входа: публично доступно подписанное discovery, но RPC настройки
требуют одноразовый секрет поверх закреплённого TLS. До завершения настройки
доступны только manifest, challenge, регистрация/вход и атомарный ClaimOwner.
После ClaimOwner сервер закрывает свободную регистрацию перед открытием обычного
входа. Секрет удаляется из RPC-соединения клиента и не записывается в его vault.
