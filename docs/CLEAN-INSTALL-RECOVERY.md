# Восстановление полного устройства на чистой установке

Стенд выполняется только в GitHub CI на Windows. Он использует настоящие
DPAPI, SharedPreferences, Rust MLS, сервер пространства и PostgreSQL из
проверенного runtime. Каждая фаза запускается в новом процессе Flutter.

Сначала создаются владелец пространства, второй участник, закрытый канал,
история и зашифрованное вложение. Полный экспорт `.spacedevice` выполняется
обычным `DeviceMigration` с пустым паролем: это разрешённый пользователем
вариант. Пустой пароль не обеспечивает секретность файла; хранить такой архив
нужно как сами рабочие ключи.

После экспорта отдельный процесс проверяет остановку исходного устройства.
Затем стенд удаляет только свой временный исходный профиль и исходную базу
внутри RUNNER_TEMP. Получатель начинает с пустых системных настроек и vault;
ему доступны архив и публичные ожидаемые идентификаторы, но не исходный vault.

После восстановления ещё один процесс проверяет идентичность сервера,
пользователя и grant, ключ устройства по отпечатку, настройки и черновик.
Он запускает восстановленную PostgreSQL, читает прежнюю MLS-историю,
расшифровывает вложение и обменивается сообщениями со вторым участником.
Повторное применение того же архива после переписки должно сохранить новое
состояние MLS и изменённые настройки. Следующий холодный запуск повторно
проверяет историю и возможность продолжить переписку.

У второго участника отдельное постоянное файловое тестовое хранилище;
оно не является источником ключей восстанавливаемого владельца. Архивы,
DPAPI-файлы, данные участников и база не публикуются как артефакты. Отчёт
содержит только результаты фаз. При любой ошибке workflow завершается неуспешно.

Это проверка чистого профиля на новой CI-машине, а не физическая переустановка
Windows, сбой питания или приёмка Android/Linux/macOS. Их покрытие указывается
отдельно. Результат CI будет добавлен после успешного прогона.
