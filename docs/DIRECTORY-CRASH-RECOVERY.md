# Аварийное восстановление передачи и применения каталога

Стенд подготовки 0.8.0 запускается только в GitHub CI. Это отдельное нативное
Flutter-приложение на Linux, собранное из `test/probes/directory_crash_probe.dart`.
Оно вызывает производственные `DirectoryTransfer`, Snow через FFI,
`DirectoryBackupService`, `DirectoryRepository`, `KeyIdentityVault` и
`AppPreferences`; сервер relay настоящий, с PostgreSQL.

## Изоляция и управление процессами

Аналогичная матрица на macOS с настоящим системным login Keychain прошла
[GitHub CI](https://github.com/space-protocol-project/space-app/actions/runs/40882808496):
17 проверок, 13 SIGKILL, 57 независимых чтений и 28 очисток собственных профилей.
[Конфигурация unsigned-сборки, правила сохранения ключей и границы](MACOS-DIRECTORY-CRASH.md).

Python-координатор создаёт новый каталог внутри `RUNNER_TEMP`, отдельные профили
источника и получателя, отдельный D-Bus для каждого GtkApplication и собственные
группы процессов. Перед `SIGKILL` он сверяет PID нативного приложения из контрольной
точки с группой созданного дочернего процесса. Завершение подтверждается кодом
сигнала; `dispose`, `finally` и штатная очистка приложения не исполняются.
Чужие группы и группа координатора не завершаются.

Перезапуск — новый процесс с тем же профилем, не горячий перезапуск Dart-изолята.
Настройки действительно записываются плагином SharedPreferences Linux, а
`XDG_DATA_HOME`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME` разделяют профили. Защищённое
хранилище в новом сценарии использует штатный `PlatformKeyStorage`, libsecret
и GNOME Keyring. При каждом холодном запуске создаются новый D-Bus и новый процесс
Secret Service; зашифрованный `login.keyring` сохраняется в изолированном профиле.
Непустой пароль стенда относится только к синтетическим данным CI.
`SECRET_BACKEND=service` запрещает файловый backend libsecret. Отдельный
`secret-tool` читает запись плагина через Secret Service и сверяет её с каталогом;
проверяются бинарный файл keyring и отсутствие прежней файловой фикстуры.
Секреты и файлы хранилища не публикуются. Проверка отключения питания и сбоя ОС
не выполняется; синтетические ключи личности не принадлежат пользователю.

Результат Linux-стенда от 29 октября подтверждён GitHub CI ниже.
Исторические результаты от 27 октября относятся к файловой фикстуре.

## Матрица остановок

| Контрольная точка | Действие после SIGKILL и нового запуска |
| --- | --- |
| Создан запрос и живой Noise handle, handshake ещё не закончен | Старый handle отклоняется до создания нового контекста; прежний профиль сохраняется |
| Получатель принял первый зашифрованный кадр | Получатель и источник завершены; частичный каталог не применён |
| Каталог проверен и передан в preview, подтверждения применения нет | Preview теряется с процессом; настройки, журнал и личности не изменены |
| Применение подтверждено, запись журнала ещё не началась | `resume()` ничего не применяет; нужен новый подтверждённый перенос |
| Журнал записан, применение ещё не началось | `resume()` завершает сохранённый план; отдельно проверяются оба значения выбора замены настроек |
| Настройки записаны, уведомления ещё не завершены | Для явно выбранной замены `resume()` доводит все параметры до снимка |
| Первое пространство сохранено | Завершается весь список без дубликатов; проверяются оба значения выбора настроек |
| Очищенный журнал записан перед подтверждением записи вызывающему коду | Новый запуск видит завершение, повтор `resume()` ничего не меняет; оба значения выбора настроек |
| Источник завершён после первого кадра, получатель остаётся жив | Получатель дожидается настоящего пятиминутного срока, закрывает канал и сохраняет исходный профиль; часы и срок не подменяются |

Для незавершённых передач и остановки до записи журнала выполняется новый
успешный перенос на тот же профиль. Новый запрос обязан получить другой ID,
другой публичный ключ и, если прежний обмен дошёл до сверки, другой SAS.
Номер старого native handle сохраняется только контрольным кодом стенда для
отрицательной проверки. Производственный код не сериализует handle или ключи
Noise. Номер handle локален процессу и не является переносимой сессией.

## Проверяемые данные

Источник передаёт два пространства со снимками по 1500 подписок: данных достаточно
для нескольких настоящих зашифрованных кадров. У получателя заранее есть третье
пространство, собственная личность и отличающиеся настройки. После восстановления
проверяются содержимое каталога, ревизия и digest головы, отсутствие pending-журнала,
порядок пространств без повторов, сохранность прежней личности и отсутствие
новых device keys для импортированных пространств.

Изменение ключа сервера и principal старой личности отвергается. Повтор
`resume()` идемпотентен. Снимки подписок сохраняются, но без подключённых
авторизованных сессий `restoreFollowing()` их не применяет и каталог не изменяет.
Успешное добавление подписок, права и ревизии API покрываются отдельными тестами;
этот сценарий не выдаёт фикстурные данные за настоящую авторизацию.

Продолжение применения вызывает тот же `resume()`, что и команда продолжения
восстановления в настройках. Сам запуск приложения не считается новым согласием
на импорт или замену настроек.

## Запуск и свидетельства

Workflow `directory-pairing.yml`, параметр `crash: true`: сборка нативного стенда,
затем `tools/check_directory_crash.py` под Xvfb. В локальной среде координатор
отказывается работать. Результат публикуется артефактом `directory-crash-recovery`:
`report.json`, журналы и контрольные точки с PID. Файлы профилей/vault в артефакт
не включаются. Итоговая строка `DIRECTORY_CRASH_CI_OK` появляется только после
завершения всех проверок.

## Windows: настоящее системное хранилище

Workflow `directory-windows-crash.yml` использует тот же нативный стенд
и настоящий сервер пространства с отдельной PostgreSQL. `PlatformKeyStorage`
вызывает рабочий Windows DPAPI backend. Файлового заменителя нет: меняется
только путь к изолированному профилю внутри `RUNNER_TEMP`; SharedPreferences
также используют настоящий дисковый backend. Копии одной сборки с разными путями
exe позволяют независимо запустить источник и получателя без изменения
защиты от второго экземпляра в рабочем приложении.

Координатор проверяет точный PID созданного процесса перед `TerminateProcess`
и ненулевой код завершения. Все прежние контрольные точки выполняются на Windows.
Дополнительная остановка происходит после записи половины зашифрованного
временного файла журнала и flush, до атомарной замены активной записи.
Используется существующий checkpoint зависимости, доступный только сборке
с `SPACE_VAULT_CRASH_TEST=true`. После обрыва прежняя запись должна читаться,
неподтверждённый каталог не применяется, новый перенос завершается успешно.

Холодный запуск проверяет прежние ключи, доверие, настройки, снимки подписок,
завершение журнала без дубликатов и отказ старых Noise handles. Отдельный
`storage-proof.json` подтверждает DPAPI-заголовок активного файла и отсутствие
файловой фикстуры; расшифрование и содержимое проверяются рабочим backend.
Артефакт содержит только отчёт, журналы и контрольные точки, без каталогов
профилей, ключей и файлов хранилища.
Завершение процесса не моделирует сбой питания, ядра ОС или повреждение диска.
