# Проверка экспериментальной интеграции MLS

Дата: 15 октября 2026. Изменения находятся в рабочих копиях space-app, space-server и space-protocol; новый выпуск не публиковался. Опубликованный runtime v0.3.0 не поддерживает новые RPC. Рабочий сервер пользователя не изменялся; проверки выполнялись отдельным процессом на временной схеме PostgreSQL.

## Что реализовано

- Группа до 256 устройств: каждое устройство — отдельный leaf. Поддерживаются KeyPackage, Welcome, Add/Remove/Commit, private application messages. Тест ядра проверяет четыре устройства; сквозной тест — три независимых клиента.
- MLS signing key подписан существующим ключом устройства и связан с server ID, principal ID, grant ID и device public key. При регистрации сервер сверяет привязку с аутентифицированным grant; после ротации использует проверенный маршрут от нового grant к историческому MLS leaf. Пользователь независимо сверяет код устройства; один серверный ответ доверия не создаёт. Код считается по однозначному массиву полей. Автор Welcome и сообщений сверяется с криптографической подписью.
- Защищённое хранилище ОС содержит snapshot, ключ снимка, revision, доверенные устройства, локальные сообщения и очередь. Обновления одного устройства сериализованы, предусмотрена межпроцессная файловая блокировка. Ошибка записи не подтверждает новое состояние. При сетевом повторе отправляется сохранённый ciphertext с тем же request ID.
- Серверные миграции 015–017 и отдельный MlsService: регистрация ключей, упорядоченная доставка, идемпотентность, блокировка эпохи, потребление KeyPackage, ACL, ограничения размеров и членства. Открытые Content-методы запрещены для MLS-канала. Режим канала неизменяем; клиент закрепляет group ID и не допускает незаметного понижения до открытого канала.
- Вложения шифруются до загрузки отдельным случайным ключом XChaCha20-Poly1305. Имя, ключ, nonce и привязка asset находятся внутри MLS payload. Сервер получает имя encrypted-file и непрозрачные байты. Квоты применяются, учитывается 16-байтовый tag. Опубликованный blob нельзя отменить как незавершённую загрузку.
- Flutter использует небольшой Rust FFI в отдельном isolate и события flutter_bloc. Есть создание закрытого канала, коды устройств, приглашение/исключение, переписка и файлы. Панель файлов группирует локальную историю по датам и фильтрует по автору. Запрет вложений выбранного сервера скрывает элементы файлов и приостанавливает их отправку.
- Нативные библиотеки автоматически собираются Dart native hooks. Rust 1.99.0 и зависимости закреплены. Уведомления 149 внешних crates для поставляемых целей и стандартной библиотеки Rust включены в раздел лицензий приложения. Сборщик уведомлений: tools/collect_mls_notices.py.

Дополнительные отрицательные сценарии: подмена binding/Welcome/сообщения/файла, неверная группа или checkpoint, повтор полученного ciphertext после перезапуска, чужое локальное устройство, неуполномоченный Commit и неверный состав. Восстановление проверено после уничтожения объектов и чтения сериализованного снимка, также с неподтверждённым Commit и с KeyPackage до Welcome. Это не заменяет ручную проверку аварийного завершения процесса на каждом устройстве. Ошибочные входящие пакеты обрабатываются на отдельном состоянии и не расходуют ключи подлинного пакета.

Серверный тест подтверждает: при отзыве устройства новые application-пакеты отклоняются до MLS Remove; после удаления доставка возобновляется. Смена root текущего устройства сохраняет его стабильный MLS leaf через таблицу mls_device_routes; старое разрешение входа отзывается. Профиль root-rotation-v2 сохраняет явно подтверждённые рабочие устройства той же идентичности без MLS Remove; сервер повторно проверяет их права, ключи и сроки в транзакции завершения. Старые пространства проходят миграции в общем наборе Go-тестов.

Воспроизведение сквозной проверки на Windows с отдельной локальной PostgreSQL:

```powershell
./tools/check_attachments.ps1 -DatabaseUrl $env:SPACE_TEST_DATABASE_URL -PostgresBin $env:SPACE_TEST_POSTGRES_BIN -Scenario mls
```

Скрипт создаёт временную схему, проверяет server ID, запускает собственный сервер и удаляет схему/процесс в finally. Не использовать рабочую базу.

## Открытые ограничения

1. Режим экспериментальный: внешнего crypto review и проверки с независимой MLS-библиотекой нет. Удалённый CI текущих изменений не запускался; macOS/Linux и физический Android ещё не приняты.
2. Проверка root/device/recovery/rotation proofs реализована для сохранения собственных устройств при смене root. Первичное доверие к MLS-ключам участников по-прежнему требует независимой сверки кода устройства, связанного с пространством и grant.
3. Полный согласованный откат всего защищённого хранилища ОС не обнаруживается независимым аппаратным счётчиком. Revision и AEAD выявляют несовпадение checkpoint/повреждение, но не дают абсолютной защиты от такого отката.
4. Новое устройство получает будущие сообщения, старую историю автоматически не получает. Recovery-карточка Space не восстанавливает MLS-ключи и историю. Перенос/резервная копия MLS-состояния и миграция снимков между версиями OpenMLS требуют отдельной реализации.
5. Передача роли и смена root текущего устройства реализованы. Передать роль можно другому активному устройству канала с правом записи; прежний управляющий остаётся участником. Самостоятельный выход и восстановление после потери всех управляющих устройств ещё требуют отдельного сценария. Действующие устройства сохраняются по подписанному списку. Отозванные и просроченные grants не восстанавливаются; их активные MLS-членства требуют Remove/Commit. Смена root сама по себе не меняет секреты MLS.
6. Отзыв grant сам по себе не удаляет leaf. Управляющий должен сделать Remove/Commit. Сервер блокирует отправку при недействующем устройстве, но криптографическое исключение обеспечивает именно новая MLS-эпоха. Злонамеренный сервер может скрывать события отзыва или нарушать доставку.
7. Точная очередь сообщений сохраняется после шифрования и до RPC. Предшествующий этап загрузки blob ещё не имеет долговременного возобновления; сбой может оставить незавершённый файл до обычной очистки. Окончательно отклонённые Commit нуждаются в явном сценарии отмены/повторного приглашения; пока полностью обработан конфликт ожидаемой эпохи, а не вся матрица отказов.
8. Полный паритет с открытым чатом ещё не реализован: редактирование/удаление, поиск, расширенное форматирование, перенос истории и полноценный просмотр без сети остаются в плане. Файловая панель показывает только полученную локальную историю.
9. Сервер видит состав группы, время, размеры, сетевые адреса и служебные идентификаторы. Вложения целиком шифруются/расшифровываются в памяти в пределах 20 МиБ, до пяти на сообщение. MLS не защищает заражённое устройство и не делает переписку анонимной.

Активный план: space-protocol/TODO.md, решение: docs/adr/034-mls-private-channels.md в репозитории протокола. Готовность всего E2EE milestone не заявляется.

Примечание к локальной сборке: после тестов `--no-pub` оставил Android-регистратор с integration_test. Обычный `flutter build apk --release` пересоздал его и завершился успешно. Сгенерированный Java-файл вручную не менялся.

## Передача управления, ротация и локальные инструменты

Продолжение 15 октября 2026:

- Передача роли — отдельный зашифрованный payload `manager`, отделённый от текста и вложений. Подмена kind/target отвергается. Клиенты сверяют текущего управляющего по локальной истории; сервер — по mls_channels.manager_grant_id в транзакции упорядоченной доставки. Идемпотентный повтор возвращает исходный результат даже после перехода роли. Удалить действующего управляющего до передачи роли нельзя.
- Стабильный MLS leaf связан с текущим grant таблицей mls_device_routes. Только штатная ротация с проверенными старой/новой root-подписями переводит маршрут на новый grant. Идентичность группы и ключи локальной истории не пересоздаются; старое разрешение входа больше не действует. Проверки активности roster/KeyPackage/файлов учитывают новый grant.
- Сквозной тест: передача A → B → A, две смены root B, сохранение кода MLS, чтение прежней истории и файлов, в том числе собственного файла B, новые сообщения, исключение B. Дополнительно проверен сбой записи новой идентичности после commit и завершение по сохранённому журналу без старого сеанса.
- Серверные отрицательные тесты: самозахват роли, передача постороннему, действия прежнего управляющего, удаление текущего управляющего, повтор передачи. Участник без глобальных административных прав после корректной передачи управляет составом своей MLS-группы.
- Инструменты Rust, Cargo target, анализатор, грамматики, отчёты и тестовая PostgreSQL находятся в `.local/mls` и исключены из Git. Подготовка PowerShell: `. ./tools/mls_environment.ps1`. Данные и сборки не должны требовать прежних путей E: для MLS. Android SDK/JDK/Gradle размещены в `.local/android`; окружение задаётся `. ./tools/android_environment.ps1`.
- Рабочий runtime пользователя не изменялся. Удалённый CI и выпуск этой версии не выполнялись. Внешний криптоаудит и физический Android остаются открытыми.

После добавления передачи управления отдельные проверки подтверждают, что отказ сервера (например, у выбранного устройства нет права записи) снимает эту команду с очереди и не блокирует последующую переписку. Сетевые ошибки сохраняют исходный ciphertext для точного повтора. Идемпотентный серверный повтор проверяется до права записи, поэтому уже принятая операция может подтвердиться после изменения прав.

Перенос каталогов: Rust/Cargo и анализатор запускаются из `.local/mls`; `client/build` — обычный каталог C:, без junction на E:. Старая тестовая база на E: сохранена как неиспользуемая копия; работающая тестовая база — `.local/mls/postgres`. На E: остаются пустые каталоги и исходные символические ссылки Rust: автоматическая проверка отклонила их удаление с причиной «blocked by policy». Повторное удаление не выполнялось. Android SDK/JDK/Gradle затем скопированы на C: в `.local/android`; `android/local.properties` и скрипт окружения используют C:. Исходные копии на E: не удалялись.

Итоговая проверка текущего шага: 351 Flutter-тест проходит, 8 пропущены по условиям запуска; 23 Rust-теста проходят; go test ./... с отдельной PostgreSQL и go vet ./... проходят. buf lint и flutter analyze без замечаний. Измерены 1907 production-функций Dart и 432 Go, максимум COG 15. Итоговые Windows Release и три Android APK собраны на C:. Тестовая PostgreSQL остановлена.


## Сохранение остальных устройств при смене root

- Профиль `root-rotation-v2` добавляет `retained_devices_hash`. Обе подписи используют отдельные домены `/v2`. Прежний профиль `/v1` остаётся для смены без сохраняемых устройств.
- До подписи клиент проверяет исходные root/recovery-подписи каждого сохраняемого устройства либо его доказательство из последней подписанной смены root. Одного списка сервера недостаточно. Список отсортирован по grant ID, без дубликатов, не более 256 устройств кроме инициатора.
- В листья дерева входят `expires_at, grant_id, public_key, scopes` в каноническом ASCII JSON. SHA-256 использует разные домены для листа, узла и итогового обязательства; итог связывает также число листьев (uint32 big endian). На нечётном уровне последний узел дублируется. Полный список хранится в БД, короткий hash — в истории root, индивидуальная ветвь — в ответе входа.
- Перед подписью интерфейс показывает ID, публичные ключи, права и сроки всех сохраняемых устройств. Отпечаток просмотренного списка сравнивается с повторно проверенным списком непосредственно перед подготовкой; изменение списка отменяет операцию.
- Подписываются неизменные ключи, права и сроки. Перед commit сервер повторно проверяет их под блокировками; отзыв, истечение, изменение прав/ключа/срока или недействительный родитель прерывают всю операцию. Recovery-разрешения и неподтверждённые сопряжения не сохраняются.
- Все прежние сеансы удаляются. Сохранённый рабочий grant получает новую auth epoch, сохраняя ID, ключ, scopes и expiry; прежний recovery-родитель отсоединяется только по новой root-подписи. Старый root и recovery остаются отозванными.
- Другое устройство при входе проверяет продолжение своей закреплённой цепочки и включение именно своего ключа/ID/прав/срока. Новая публичная история сначала сохраняется в защищённый vault. Старые root/recovery-секреты удаляются из активной записи; новый root-секрет другим устройствам не передаётся. Ошибка записи позволяет повторить вход с прежней локальной записью.
- MLS leaf, подписанный binding, checkpoint, outbox и история не пересоздаются. Отозванные устройства не восстанавливаются; их криптографическое исключение по-прежнему требует Remove/Commit.
- Новая миграция — 017. Работающий домашний runtime и его БД при разработке не менялись. Автоматическая проверка отклонила запрошенное удаление `client/build` с причиной `blocked by policy`; обход не выполнялся.


Проверка путей сборки выявила прежние junction `client/android/.gradle` и `client/.dart_tool/flutter_build`. Они перенесены как неиспользуемые ссылки в `.local`, вместо них созданы обычные каталоги на C:. Финальные сборки запускаются после этой замены. Исходные каталоги и данные на E: не удалялись.


Для текущего Flutter SDK release-сборки после тестов выполняются обычными командами `flutter build windows --release` и `flutter build apk --release --split-per-abi`: шаг pub также обновляет платформенную регистрацию без dev-плагина integration_test. Сборка с `--no-pub` после debug/test-генерации может оставить прежнюю регистрацию.


Проверка продолжения закреплённой root-цепочки не заменяет внешний журнал прозрачности: она не обнаруживает сокрытие ещё не увиденной смены ключа сервером. Полный согласованный откат локального хранилища также требует независимого якоря версии. Смена root не заменяет криптографическое исключение скомпрометированного MLS leaf.


Дополнительно исправлена потеря TLS-отпечатка в новой записи инициатора ротации. Отдельный тест подготовки проверяет сохранение fingerprint, endpoint и серверной идентичности; он не выполняет настоящий HTTPS-запрос. Расчёт допустимого размера recovery-карточки теперь учитывает endpoint и TLS-отпечаток. Сохраняемые grants проверяются клиентом по допустимым рабочим scopes независимо от серверного флага recovery: скрыто включить recovery или неизвестные права в подписываемый список нельзя.
